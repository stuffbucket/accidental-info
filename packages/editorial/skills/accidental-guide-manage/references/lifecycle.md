# Portfolio lifecycle

## Sources of truth

| Concern | Source |
|---|---|
| Collection, group, display order and map code | `site/src/data/collections.json` |
| Draft or published state | Folder under `drafts/` or `guides/` |
| Guide title, version and imprint | The folder's `guide.md` |
| Concept owner, family and tile code | `packages/editorial/registry.json` |
| Workspace packages and cover metadata | Generated by `pnpm sync` |
| Release identity | `<slug>-v<version>` |

Do not maintain a second roadmap with different slugs or placement. Notes may explain a proposal, but the taxonomy reserves its public identity.

## States

### Proposed

The reader, question and likely group are known. No public identity is reserved.

### Planned

A `coming` entry reserves the slug, title, placement and map code. Concept candidates are checked against the registry.

### Draft

A matching folder exists under `drafts/`. The site promotes the `coming` entry into a real guide at the same position.

### Published

The same folder moves to `guides/`. A published guide has accepted PDF and Word output, a deterministic hash and a release tag.

### Retired

The old slug, map code and concept codes remain unavailable. Redirects and replacement guidance are a site concern, not a reason to reuse an identity.

## Change rules

- Rename before the first release where possible.
- Treat a published slug as permanent.
- Append new entries after published entries to preserve cover numbers.
- Move a published entry only with an explicit renumbering and release plan.
- Keep provider catalogs in references unless one provider raises a durable reader question.
- Run both portfolio and registry checks before creating a draft.
